# Реализация протокола в этом репозитории и отклонения

Сверено с Протоколом v1.2.05 от 09.06.2021 (127 с.). Дата сверки —
2026-10-29. Протокол — источник истины; всё ниже описывает текущее состояние
кода и расхождения с ним.

## Что уже реализовано

| Команда | Статус | Особенности |
|---|---|---|
| `30h` | да | Ожидается 30 байт данных; разбираются этап, смена, флаги, дата/время, SN, № последнего ФД |
| `32h` | да | 5 байт: дата окончания, осталось регистраций, выполнено |
| `33h` | да | 17 байт: ASCII 16 + тип ПО |
| `3Ah` | да | 2 байта: текущий и максимальный код ФФД |
| `3Bh` | да | Дата/время из RTC, ожидается 2 байта (дни) |
| `3Dh` | да, с дефектом | Ожидается ровно 9 байт — см. ниже |
| `60h` | да | Сброс МГМ, данные `16h`, таймаут 30 с — **не описана в Протоколе** |
| `31h`, `35h`, `3Fh`, `36h`–`39h`, `10h`, `40h`–`47h`, `50h`, `B*h` | нет | При добавлении сверяйся с `service-commands.md` / `archive-commands.md` |

`fn_tool_get_fn_info()` выполняет три команды подряд: `30h` → `3Ah` → `33h`.
`fn_tool_get_fn_life_data()` — `32h` → `3Dh` → `3Bh` (последняя только для
этапов 2 и 3).

## Транспорт и кадры

- USART (`FuriHalSerialIdUsart`, пины 13/14), 115200 8N1.
- На время работы отключается обнаружение модулей расширения
  (`expansion_disable`), при выходе включается обратно.
- RX — DMA; `UARTApp::rx_ready` выставляется после запуска DMA.
  `fn_uart_trx()` ждёт `rx_ready` до 100 мс, иначе возвращает `false`.
- Поток UART: стек 1 КБ, приоритет `FuriThreadPriorityIsr`, таймаут взводится
  `FuriTimer`.
- Поток воркера: стек 10240, режимы `Idle`/`FNDetect`/`GetLifeInfo`/`FlashMGM`.
- Таймаут служебных команд — 300 мс, сброса МГМ — 30 000 мс.

`fn_trx()` собирает кадр так: `04`, LEN (функция с именем `..._BE_to_...`, но
пишет младший байт первым), CMD, DATA, CRC (младший байт первым). Это
соответствует Протоколу.

## Ловушка с именами helper-функций

Имена в `fn_helpers.c` противоположны общепринятому смыслу:

| Функция | Что реально делает |
|---|---|
| `two_uint8t_to_uint16t_LE(b)` | возвращает `b[0] << 8 | b[1]` — **big-endian** значение |
| `two_uint8t_to_uint16t_BE(b)` | возвращает `b[1] << 8 | b[0]` — **little-endian** значение |
| `uint16t_LE_to_uint8t_bytes(v)` | пишет `[v >> 8, v]` — **BE** на проводе |
| `uint16t_BE_to_uint8t_bytes(v)` | пишет `[v, v >> 8]` — **LE** на проводе |

Поэтому в `fn_tools.c` длина ответа и дни до окончания читаются через
«`BE`»-функцию и получают правильные LE-значения, а CRC — через «`LE`»,
согласованно с `calc_crc16()`, который возвращает байтово-переставленное
значение.

**Не переименовывай и не «чини» эти функции по названию без одновременной
правки всех вызовов, `calc_crc16()` и `check_crc()`.** Если вводишь стандартные
`u16le`/`u32le`, переписывай слой целиком и добавляй тесты на реальных кадрах.

## Найденные расхождения с Протоколом

### 1. `3Dh`: необязательный третий байт и выход за границу (дефект)

Протокол (4.2.7): ответ — 4 + 4 байта, третий байт (процент уведомлений)
возвращается только для ФН в режиме ФФД 1.2. Код:

- требует `check_data_len(..., 9)` — для ФН без маркировки (8 байт) операция
  завершится ошибкой длины;
- читает `data[data_len]`, то есть на 1 байт за пределами буфера; должно быть
  `data[8]` и только при `data_len >= 9`.

Правильное поведение: принять 8 или 9 байт; третий байт учитывать только при
наличии (и только для ФФД 1.2).

### 2. `3Dh`: «30-дневный» назван «30-летним»

Поле `thirty_year_data_resource` и подпись «Thirty year data resource» в UI
означают ресурс **30-дневного** хранения (КБ), а не 30 лет. Название вводит в
заблуждение при сопровождении.

### 3. `33h`: «тип ПО = 0» как признак МГМ

`fn_is_mgm()` возвращает `!fw_mode`. По Протоколу `0` — опытный образец, `1` —
серийное изделие; отдельного признака МГМ в документе нет. Эвристика проекта
допустима для тестовых ФН, но не является требованием Протокола и не должна
использоваться для боевых накопителей.

### 4. `60h` не описана в Протоколе

Команда `60h` с данными `16h` — расширение для сброса тестового МГМ. В
документе v1.2.05 её нет. Формат и поведение считаются проектным знанием;
при работе с боевым ФН команду отправлять нельзя (принцип I конституции).

### 5. Неполный справочник кодов ответов

`FNError` содержит только `00h`, `01h`, `02h`, `03h`, `04h`, `05h`, `07h`,
`08h`. Отсутствуют как минимум `09h`, `0Ah`, `0Bh`, `0Ch`, `0Dh`, `0Eh`,
`10h`, `11h`, `12h`, `14h`, `16h`–`19h`, `20h`, `23h`, `24h`, `30h`, `32h`–
`36h`, `3Ch`, `3Eh`. Неизвестный код сейчас отображается как ошибка без
описания — при добавлении кодов сверяйся с `response-codes.md`.

### 6. Не парсится байт «Данные документа» (`30h`, смещение 2)

Сейчас читаются смещения 0, 3, 4, 5–9, 10–25, 26–29. Смещение 2 (признак
наличия данных документа) не используется — это допустимо, но при добавлении
экрана «текущий документ» его нужно учитывать, чтобы не показывать пустой
документ как открытый.

## Куда добавлять новую команду

1. Код — в `lib/fn/fn_commands.h` с комментарием и ссылкой на раздел Протокола.
2. Сборка запроса и разбор ответа — в `lib/fn/fn_tools.c` по образцу
   `fn_tool_get_fn_life_data()`; проверяй `check_data_len` по фактическому
   размеру из Протокола.
3. Поля — в соответствующую структуру (`FNInfo`, `FNLifeInfo`) и геттеры.
4. Событие/режим — в `FNWorker` (`fn_worker.h`, `fn_worker_modes.c`) и
   `fn_worker_i.h`.
5. Тест — `unit_tests/lib_tests/fn/...`, с реальным или эталонным кадром.
6. Экран/сцена — только через события воркера, без прямого UART из UI.

## Тестирование

- `unit_tests/lib_tests/fn/uart/fn_uart_test.c` — запуск/останов потока,
  коллбек, обмен (требует реального ФН, иначе `[SKIP]`).
- `unit_tests/lib_tests/fn/fn_objects/fn_info_test.c` — разбор реального
  ответа `30h` (эталонные байты в тесте).
- `unit_tests/lib_tests/fn/fn_objects/fn_life_info_test.c` — жизненный цикл.
- Профиль: `FN_TESTS=1 ufbt launch`; запуск: `python3 .test_scripts/units.py <имя>`.

Для `3Dh` тест обязан покрыть оба случая: 8 байт (без маркировки) и 9 байт
(ФФД 1.2), а также отсутствие чтения за границей буфера.
