# Проверка UI на устройстве по USB (RPC, protobuf)

Этот способ позволяет автоматизировать приёмочные сценарии на реальном Flipper:
отправлять нажатия, снимать кадры экрана и менять файлы на SD — без ручного участия.
Так проверяются сценарии вида «нажать OK 3 раза, дождаться конца отсчёта, убедиться,
что на экране `Pours 3 / 2` и плашка `OVER`».

## 1. Подготовка окружения

```bash
python3.11 -m venv ~/.venvs/flipper-rpc
~/.venvs/flipper-rpc/bin/pip install flipperzero-protobuf pillow
```

`flipperzero-protobuf` (пакет от flipperzero) даёт класс `FlipperProto` с RPC-методами:
GUI, Storage, App, System. `pillow` нужен только чтобы сохранять кадры в PNG для глаз.

## 2. Подключение к устройству

```python
from flipperzero_protobuf import FlipperProto

PORT = "/dev/cu.usbmodemflip_XXXX"   # macOS; Linux: /dev/ttyACM0
fp = FlipperProto(PORT)              # порт указывать ВСЕГДА явно
```

- **Порт обязателен.** Без явного порта конструктор может надолго зависнуть на
  автоопределении, особенно если подключено несколько устройств или открыт `ufbt cli`.
- Порт — тот же CDC, что у CLI. **RPC и `ufbt cli` одновременно не работают**:
  пока идёт RPC-сессия, логи через CLI не почитать. Если нужны и логи, и сценарий:
  сначала прогон с логами, потом прогон по RPC (или писать диагностику в файл на SD).
- Найти порт: `ls /dev/cu.usbmodemflip_*` (macOS) / `ls /dev/ttyACM*` (Linux).

## 3. Кадр экрана

```python
data = fp.rpc_gui_snapshot_screen()   # ровно 1024 байта
```

Формат — как у u8g2: страницы по 8 вертикальных пикселей,
`buffer[(y // 8) * 128 + x]`, бит `1 << (y % 8)`. `1` = чёрный пиксель, `0` = белый.
Экран 128×64, поэтому 8 страниц × 128 байт.

Мини-конвертер в PNG (для визуальной проверки):

```python
from PIL import Image

def framebuffer_to_image(data: bytes) -> Image.Image:
    im = Image.new("1", (128, 64), 1)
    px = im.load()
    for y in range(64):
        page, bit = (y // 8) * 128, 1 << (y % 8)
        for x in range(128):
            if data[page + x] & bit:
                px[x, y] = 0
    return im

framebuffer_to_image(fp.rpc_gui_snapshot_screen()).resize((512, 256), Image.NEAREST).save("shot.png")
```

### 3.1 Как убедиться, что кадр разобран верно (проверяй всегда!)

Формула выше (`page = (y // 8) * 128`, бит `1 << (y % 8)`) — единственно верная для
прошивок 1.5.x–1.6.x. Ошибка в раскладке коварна: **крупная графика, иконки и статус-бар
выглядят правдоподобно**, а мелкий шрифт (`FontSecondary`, `FontKeyboard` 5×7) рассыпается
в «полоски». Это очень легко принять за баг приложения — зависший экран, «битые» строки
в submenu, dangling-указатели — и искать проблему, которой нет.

Проверка за 10 секунд: вывести кадр текстом и **прочитать надписи**.

```python
def ascii_dump(data: bytes, y0: int = 0, y1: int = 63) -> str:
    lines = []
    for y in range(y0, y1 + 1):
        page, bit = (y // 8) * 128, 1 << (y % 8)
        lines.append("".join("#" if data[page + x] & bit else "." for x in range(128)))
    return "\n".join(lines)

print(ascii_dump(fp.rpc_gui_snapshot_screen(), 0, 20))
```

Признаки:
- мелкий текст **читается** — раскладка верная;
- вместо букв идут равноотстоящие полоски, а иконка/логотип выглядят «нормально» —
  раскладка неверная, и «сломанный экран» относится к разбору, а не к приложению.

Типичные неверные варианты, которые дают «почти картинку» (не использовать):

| Ошибка | Как выглядит |
|---|---|
| `((y // 8) * 16 + (x // 8)) * 8 + (x % 8)` — тайлы 8×8 по 16 в строке | крупное и симметричное (иконки, логотип) сходится, текст — мусор |
| бит `1 << (7 - (y % 8))` — старший бит вверху | кадр «перевёрнут по вертикали внутри каждой страницы» |
| инверсия «белое ↔ чёрное» | картинка читаемая, но негативная |

Практический приём: если приложение на экране «выглядит сломанным», сначала нажми на
устройстве клавишу и сними кадр ещё раз, и только затем проверяй код. Часто оказывается,
что устройство просто висит на экране `CRITICAL ERROR` от предыдущего прогона — его видно
на снимке, если разбор верный.

## 4. Нажатия

```python
fp.rpc_gui_send_input("SHORT OK")     # одно короткое нажатие
fp.rpc_gui_send_input("SHORT DOWN")
```

Ключи: `UP`, `DOWN`, `LEFT`, `RIGHT`, `OK`, `BACK`. Типы: `SHORT`, `LONG`, `PRESS`, `RELEASE`.

- RPC `rpc_gui_send_input` сам формирует полное событие (`press` → `short` → `release`),
  в отличие от CLI-команды `input send`, где нужны все три шага (иначе GUI отбросит
  событие как non-complementary).
- Вызов синхронный: после возврата событие уже доставлено. Но анимации/переходы сцен
  занимают время, поэтому после нажатия полезно подождать 0.3–1.0 с перед снимком.
- Нажатия приходят как обычный ввод: работают и кнопки `widget_add_button_element`,
  и `view_set_input_callback`, и навигация модулей.
- Нужен полностью ручной контроль тайминга (длинное нажатие, удержание) — используй
  `rpc_gui_send_input_event_request(key, "PRESS"/"SHORT"/"LONG"/"RELEASE")` и расставляй
  `time.sleep()` сам.

### 4.1 Почему не стоит водить UI через CLI `input send`

До появления RPC соблазн такой: по тому же CDC-порту слать
`input send DOWN press` / `short` / `release` обычной строкой CLI. На практике это
источник «моргающих» тестов:

- одиночный `short` без `press`/`release` GUI **отбрасывает** как non-complementary input;
- при паузах 0.1–0.3 с между частями события часть нажатий **теряется** (событие приходит
  раньше, чем view переключился), и сценарий уезжает на другой экран; рабочие паузы —
  от ~0.6 с на каждую часть, то есть один сценарий растягивается на минуты;
- пока идёт `log`, CLI занят потоком логов, и команды `input send` обрабатываются через раз.

RPC-нажатие синхронное и не зависит от скорости CLI-парсера — используй его.

### 4.2 Раскладки стандартных клавиатур (важно для сценариев)

Скрипт нажимает клавиши вслепую, поэтому надо знать точные позиции — иначе набирается
не то слово (буква `e` лежит в первой строке, а не во второй, и т.п.).

`text_input` (3 строки по 8 px), позиции задаются `RIGHT`/`LEFT`/`DOWN`/`UP` от курсора:

| Строка | Клавиши (слева направо) |
|---|---|
| 0 | q w e r t y u i o p 0 1 2 3 |
| 1 | a s d f g h j k l ⌫ 4 5 6 |
| 2 | z x c v b n m \_ \[Save\] 7 8 9 |

- `ok` вставляет выбранный символ (первый символ — заглавный, пока строка пустая);
- Завершение ввода — только клавишей **Save** (символ `\r`, строка 2, столбец 8);
  `BACK` в `text_input` не потребляется и уходит сцене как «назад»;
- если буфер уже заполнен (режим правки), курсор сразу стоит на **Save**;
- сдвиг регистра — `LONG OK` (shift).

`number_input` (2 строки): `0 1 2 3 4 ⌫` и `5 6 7 8 9 − ` **Save**.
Клавиша `−` скрыта, если диапазон не требует отрицательных чисел (тогда после `9`
сразу идёт **Save**). Цифры только добавляются в конец, удаление — `⌫`.

### 4.3 Состояние модулей переживает смену сцен

- `number_input` не имеет `number_input_reset()`: позиция курсора (строка/столбец)
  сохраняется между шагами формы и между сценами. Скрипт, рассчитанный на «курсор в (0,0)»,
  попадёт в другую клавишу. Для детерминизма перезапускай приложение между сценариями (§7).
- `submenu`/`widget` при входе в сцену обычно пересоздаются приложением — но полагайся на
  это только если видел соответствующий `*_reset()` в коде сцены.

## 5. Как проверять состояние экрана автоматически

Сравнивать кадры побайтово бесполезно: на экране идёт отсчёт/анимация. Надёжный приём —
**доля тёмных пикселей в характерной области**:

```python
def frac(data, x0, x1, y0, y1):
    dark = total = 0
    for y in range(y0, y1 + 1):
        for x in range(x0, x1 + 1):
            total += 1
            if data[(y // 8) * 128 + x] & (1 << (y % 8)):
                dark += 1
    return dark / total
```

Порядок работы:

1. Один раз сними кадр в нужном состоянии и распечатай его ASCII-артом, чтобы найти
   координаты характерного элемента:

   ```python
   d = fp.rpc_gui_snapshot_screen()
   for y in range(14, 32):
       print(y, "".join("#" if d[(y // 8) * 128 + x] & (1 << (y % 8)) else "."
                        for x in range(128)))
   ```

2. Выбери прямоугольник, который в целевом состоянии почти полностью чёрный/белый,
   а в остальных — нет. Замерь долю в обоих состояниях и поставь порог посередине.
3. Опрашивай в цикле (`time.sleep(0.1)`), пока условие не выполнится; обязательно
   ограничь общее время, чтобы тест не завис навсегда.

Пример: определение «отсчёт завершён» по инверсной плашке `Time is up!`
(прямоугольник `x=40..92, y=17..28`, доля тёмного ≈ 0.72 в DONE и ≈ 0.38 в RUNNING,
порог 0.6).

**Точность таймера.** Чтобы измерить отклонение отсчёта, запомни `time.time()` перед
`rpc_gui_send_input("SHORT OK")` и опрашивай экран до появления DONE. Погрешность метода —
время одного RPC-запроса (десятки мс) плюс интервал опроса; для критерия «≤ 1 с» этого
достаточно.

## 6. Файлы на SD через RPC

```python
fp.rpc_storage_list("/ext/apps_data/my_app")
fp.rpc_read("/ext/apps_data/my_app/preset.tea")
fp.rpc_write("/ext/apps_data/my_app/preset.tea", "name: Test\n...")
fp.rpc_mkdir("/ext/apps_data/my_app/newdir")
fp.rpc_rename_file("/ext/apps_data/my_app", "/ext/apps_data/my_app_off")
fp.rpc_delete("/ext/apps_data/my_app/file.tea")
```

- **Алиас `/data` в RPC/CLI не разворачивается**: он привязан к appid вызывающего потока,
  а у RPC/CLI это `cli_vcp`. Поэтому снаружи всегда используй реальный путь
  `/ext/apps_data/<appid>`.
- **Внутри приложения пути выглядят иначе** — и это нормально: `APP_DATA_PATH(...)` и
  `STORAGE_APP_DATA_PATH_PREFIX` дают `/data/...`, `file_browser` возвращает выбранный
  файл тоже как `/data/my_app/preset.tea`. Если в снимке экрана или в логе видно такой
  путь, а снаружи файл лежит в `/ext/apps_data/my_app/preset.tea` — никакого бага нет,
  алиас разворачивает сама прошивка внутри процесса приложения.
- `rpc_storage_list` возвращает список словарей: `{"name": "preset.tea", "type": "FILE",
  "size": 88, ...}` — бери имена как `[i["name"] for i in ...]`.
- `rpc_storage_list` с завершающим слэшем (`/ext/.../my_app/`) возвращает
  `ERROR_STORAGE_INVALID_NAME` — путь для каталога указывай без слэша.
- После `rpc_rename_file` приложения, которое уже работало, каталог может быть создан
  заново алиасом: перед обратным переименованием проверь и при необходимости
  `rpc_delete` пустой каталог.

## 7. Запуск, остановка и перезапуск приложения

```bash
ufbt launch                          # собрать, залить, запустить
ufbt APPID=my_app APP_ONLY=1 launch  # если в каталоге несколько манифестов
```

- Из скрипта приложение удобнее запускать через `ufbt launch` (шелл), а не RPC:
  команда сама заливает свежий `.fap`.
- Выход из приложения: нажать `BACK` столько раз, сколько нужно, и **проверить снимком**,
  что вернулось главное меню прошивки (`Settings / Apps / Sub-GHz`) — иначе следующий
  запуск будет «закрывать текущее приложение» вместо чистого старта.
- Между прогонами состояние сессии в приложении сохраняется, если оно живёт в памяти
  (например, счётчик проливов). Для чистого прогона перезапусти приложение.

### 7.1 Перезапуск: RPC-методы тут не работают

`rpc_app_exit()` и `rpc_app_start()` ведут себя не так, как ожидается, если приложение
запущено обычным путём (`ufbt launch`, `loader open`):

| Ситуация | Ответ | Что делать |
|---|---|---|
| `rpc_app_exit()`, приложение запущено не через RPC | `ERROR_APP_NOT_RUNNING` | не ошибка — приложение продолжает работать |
| `rpc_app_start()`, приложение уже работает | `ERROR_APP_SYSTEM_LOCKED` | не ошибка — уже запущено, можно слать нажатия |

Надёжный перезапуск — **через CLI-команды, пока RPC-сессия закрыта** (это один и тот же
CDC-порт, одновременно нельзя):

```python
import serial, time

def restart_app(port: str, fap: str = "/ext/apps/Tools/my_app.fap", settle: float = 2.5) -> None:
    """Закрыть и снова открыть FAP через CLI loader. Порт должен быть свободен от RPC."""
    ser = serial.Serial(port, 115200, timeout=0.3)
    time.sleep(0.8)
    ser.write(b"\x03")          # Ctrl+C: выйти из возможного хвоста вывода
    time.sleep(1.0)
    ser.reset_input_buffer()
    for cmd in ("loader close", "loader open %s" % fap):
        ser.write(cmd.encode() + b"\r\n")
        time.sleep(2.0)
        ser.reset_input_buffer()
    ser.close()
    time.sleep(settle)          # дать приложению дорисовать первый экран
```

Порядок в сценарии: `restart_app(...)` (обычный pyserial) → затем `FlipperProto(port)`
для нажатий и снимков. После `restart_app` главный экран приложения гарантированно
первый, а модули (`text_input`/`number_input`) — в исходном состоянии.

### 7.2 Не испортить данные пользователя на карте

UI-сценарии создания/удаления пишут и стирают файлы в `apps_data/<appid>` — там же лежат
рабочие данные владельца устройства. Перед прогоном:

1. Считать весь каталог через RPC (`rpc_storage_list` + `rpc_read`) и сохранить копии
   локально в файлы (побайтно, без преобразований).
2. Убрать файлы с карты (`rpc_rename_file` в `/ext/<appid>_bak` — быстрее и надёжнее,
   чем удалять; либо `rpc_delete`), оставив только тестовые.
3. Прогнать сценарии на предсказуемом состоянии — иначе `file_browser` покажет разное
   число строк и позиции курсора «поплывут».
4. После прогона вернуть файлы обратно и **сверить содержимое**: `rpc_read` побайтно
   равен локальной копии. Не полагайся на «размер совпал».

Проверка, что ничего не потеряно, обязательна: цена ошибки — данные пользователя,
а не тестовый стенд.

Дополнительно:

- **Локальную копию не удаляй**, пока пользователь не подтвердил приёмку. SD-карта в
  устройстве — расходник: износ, сбой питания или сбой FAT могут «съесть» каталог, и
  единственная копия тогда окажется у тебя на диске. Удаляй `*_bak` последним.
- Не вызывай `rpc_delete` на каталогах, где лежат данные пользователя, даже «пустых на
  вид»: проверяй содержимое ещё раз непосредственно перед удалением.
- Если файлы внезапно пропали из листинга — не запускай новых записей (это уменьшает
  шансы восстановления), проверь `uptime` (не перезагружалось ли устройство) и сообщи
  пользователю: восстановление делается на ПК с картой, вынутой из устройства.

## 8. CLI-команды приложения во время RPC-теста

Если приложение регистрирует CLI-команды (например, `my_app_test` для on-device
юнит-тестов), выполнить их можно только через CLI — а он занимает порт. Порядок:

1. RPC-скриптом довести приложение до нужного экрана и **закрыть RPC-сессию**
   (завершить процесс, порт освобождается).
2. Открыть `ufbt cli` в pty и отправить команды.

`ufbt cli` требует TTY, поэтому из скрипта его запускают через `pty.fork()` и пишут
команды с `\r`. После работы обязательно закрыть процесс, иначе порт останется занят
и следующий RPC-коннект зависнет.

Проще обойтись без `ufbt cli`: CLI-команды принимает сам CDC-порт. Открой его обычным
`pyserial` и пиши команду строкой с `\r\n`, читая ответ до промолчания порта:

```python
def cli(port: str, command: str, wait: float = 2.0) -> str:
    import serial, time
    ser = serial.Serial(port, 115200, timeout=0.3)
    time.sleep(0.6)
    ser.reset_input_buffer()
    ser.write(command.encode() + b"\r\n")
    end, buf = time.time() + wait, bytearray()
    while time.time() < end:
        data = ser.read(4096)
        if data:
            buf.extend(data)
    ser.close()
    return buf.decode("utf-8", "replace").replace("\r", "")
```

Так же запускаются встроенные наборы юнит-тестов (`my_app_test my_suite`): вывод
`… tests, … assertions, 0 failures`, `Leaked: 0`, `Status: PASSED` попадает в строку
ответа. Таймаут бери с запасом: прогон набора занимает ~1 с, но CLI может ответить
с задержкой.

## 9. Что RPC-тест не покрывает

- Подсветка/гашение экрана: кадр отдаётся независимо от состояния подсветки.
- Извлечение SD-карты, кнопки, заряд батареи, звук и вибро «на слух».
- Реальную скорость отрисовки (кадры снимаются по запросу, а не потоком).

Эти пункты остаются ручными — их нельзя заменить снимками экрана, но всё остальное
(навигация, тексты, счётчики, переходы состояний, точность таймера по времени)
проверяется автоматически и воспроизводимо.

## 10. Готовый каркас

`examples/rpc-ui-test/flipper_rpc.py` — помощник, в котором уже учтены все грабли выше:

- `connect(port)` — подключение с явным портом;
- `framebuffer_to_image` / `save_snapshot` — верный разбор кадра и PNG для глаз;
- `ascii_dump` — текстовая распечатка кадра, чтобы сразу увидеть ошибку раскладки;
- `press(fp, "DOWN")` — короткое нажатие полным событием;
- `dark_frac` / `wait_for_frac` — ожидание состояния по доле тёмных пикселей;
- `restart_app(port, fap)` — чистый перезапуск через CLI `loader close/open`;
- `backup_dir` / `restore_dir` — копия каталога данных и возврат с побайтной сверкой;
- `list_dir` / `read_text` / `write_text` — файлы на SD.

Запуск «показать экран и проверить, что разбор верный»:

```bash
~/.venvs/flipper-rpc/bin/python flipper_rpc.py /dev/cu.usbmodemflip_XXXX --ascii
```
