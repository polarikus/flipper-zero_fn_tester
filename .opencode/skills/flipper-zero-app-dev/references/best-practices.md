# Best practices и архитектура

## 1. Архитектура приложения

Рекомендуемое разделение:

```
app (состояние + сцены)  ──  scene (экран)  ──  view (отрисовка/ввод)
        │
        ├── worker (поток/EventLoop): UART, IR, NFC, файлы, сеть
        ├── storage (загрузка/сохранение настроек)
        └── model (чистые данные и логика, без GUI)
```

- **Держи логику отдельно от GUI.** Чистые функции/структуры легко тестировать на хосте
  (см. `references/testing.md`), а сцены остаются «клеем».
- **Одна сцена — один экран.** Не пихай несколько независимых экранов в одну сцену.
- **Состояние — в `MyApp`.** Никаких глобальных переменных: при повторном запуске
  приложения они сохранят мусор.
- **Воркер владеет потоком и ресурсом**, сцена только просит его что-то сделать и
  получает результат событием/колбэком. Это позволяет не блокировать GUI.
- **Не смешивай слои:** `view` не должен читать файлы, `worker` не должен трогать `View`.

## 2. Память

- Всегда думай о бюджете: 256 КБ RAM на всё, FAP занимает часть под свой код/данные.
- Стек главного потока (`stack_size`) — 1–2 КБ обычно достаточно для UI-приложения.
  Если в callback-ах есть большие локальные массивы, `snprintf` с длинными строками,
  рекурсия — увеличь стек или перенеси данные в кучу.
- Не создавай/не удаляй объекты в цикле отрисовки. Кэшируй `FuriString`, буферы,
  результаты форматирования.
- Проверяй `malloc` на NULL в местах, где возможен OOM (лучше — `furi_check`, чтобы
  получить предсказуемый краш вместо порчи памяти).
- Избегай фрагментации: переиспользуй буферы, используй `furi_string_reserve`.
- Диагностика: `free`, `top`, `memmgr_get_free_heap()`, `memmgr_heap_get_max_free_block()`.

## 3. Потоки и асинхронность

- GUI-поток — священный: только быстрые операции. I/O, ожидание ответа, парсинг
  больших файлов — в отдельном потоке или через `FuriEventLoop` + колбэки.
- Поток должен уметь корректно завершиться: флаг + `furi_thread_flags_set` +
  `furi_thread_join` перед `furi_thread_free`.
- Не используй `furi_delay_ms` как «синхронизацию». Для ожидания — семафоры,
  event flags, message queue, `furi_event_loop`.
- Колбэки из HAL/сервисов (UART RX, IR RX, pubsub) выполняются в чужих потоках/ISR:
  не блокируй их, не вызывай GUI-функции, не делай длинных вычислений.
- Один ресурс — один владелец. Если воркер владеет UART, сцена не должна вызывать
  `furi_hal_serial_*` напрямую.
- Таймеры: callback в timer-потоке; долгая работа в нём задерживает все таймеры.

Пример неблокирующего обновления UI из воркера:

```c
// worker thread
view_dispatcher_send_custom_event(app->view_dispatcher, MyEventDataReady);
// dispatcher thread (GUI) в scene on_event:
case MyEventDataReady:
    with_view_model(app->view, Model* m, { m->value = value; }, true);
    consumed = true;
    break;
```

## 4. UI

- Следуй системному виду: заголовок, список/контент, подсказки кнопок
  (`elements_button_center(canvas, "Start")`).
- Back должен работать всегда и предсказуемо: из корневой сцены — выход из приложения,
  из вложенной — на шаг назад (`scene_manager_previous_scene`).
- Не показывай «сырые» ошибки — объясняй пользователю, что делать («SD card not found»).
- Долгие операции показывай `Loading`/`Popup`/прогресс-баром и не блокируй экран.
- Обновляй экран по событию, а не в бесконечном `while` с `view_port_update` без паузы.
- Текст: 128 px ширины; проверяй `canvas_string_width`, переноси/обрезай.
- Не полагайся на цвет: экран монохромный; используй инверсию и рамки.
- Анимация: `IconAnimation` или кадры по таймеру; не чаще ~30 FPS.
- Диалоги (`DialogsApp`) синхронные — не вызывай их из draw/input и не держи открытыми
  во время фоновой работы.

## 5. Жизненный цикл и ресурсы

Порядок освобождения — зеркальный порядок создания:

```c
MyApp* my_app_alloc(void) {
    MyApp* app = malloc(sizeof(MyApp));
    app->gui = furi_record_open(RECORD_GUI);
    app->view_dispatcher = view_dispatcher_alloc();
    app->scene_manager = scene_manager_alloc(&handlers, app);
    view_dispatcher_attach_to_gui(app->view_dispatcher, app->gui, ViewDispatcherTypeFullscreen);
    ...
}

void my_app_free(MyApp* app) {
    view_dispatcher_remove_view(app->view_dispatcher, MyAppViewMain);
    view_dispatcher_free(app->view_dispatcher);
    scene_manager_free(app->scene_manager);
    furi_record_close(RECORD_GUI);
    free(app);
}
```

Правила:

- `remove_view` **до** `view_dispatcher_free`; `view_free` — после remove.
- `furi_record_close` — ровно один раз на `furi_record_open`.
- Перед выходом останавливай воркеры/таймеры и сбрасывай аппаратные ресурсы
  (`*_stop`, `*_release`, `*_reset`).
- При ошибке на середине `alloc` освобождай уже созданное (goto cleanup или отдельные
  функции) — не оставляй полуинициализированное состояние.

## 6. Работа с файлами

- Данные приложения — `APP_DATA_PATH("...")`; ассеты — `APP_ASSETS_PATH("...")`.
- **Каталог** приложения — без завершающего слэша: `APP_DATA_PATH("")` даёт `/data/`,
  а `storage_dir_open()`/`storage_dir_exists()` на таком пути возвращают
  `FSE_INVALID_NAME`. Используй `STORAGE_APP_DATA_PATH_PREFIX` (`"/data"`).
- Всегда `storage_file_close()`, даже если `storage_file_open()` вернул `false`.
- Проверяй ошибки `FS_Error` и показывай понятное сообщение.
- Для сохранения настроек: пиши во временный файл, затем `storage_common_rename`
  (атомарность), либо используй `saved_struct_save`.
- Не делай `storage_*` вызовы в GUI-потоке: SD-операции могут занимать десятки мс.
- Обрабатывай извлечение SD: подпишись на `StorageEventTypeCardUnmount` или проверяй
  результат операций.
- Пути: используй `FuriString` + `path_*` из toolbox, а не ручную склейку с `strcat`.

## 7. Ошибки и устойчивость

- Проверяй все внешние входы: аргументы, данные из файлов, ответы HAL.
- Используй `furi_check` для «этого не может быть»; для ожидаемых ошибок — возвращай
  код/показывай диалог.
- Никогда не игнорируй возвращаемое значение acquire/open/alloc, если от него зависит
  дальнейшая работа.
- Не доверяй длине данных из файла/эфира: ограничивай размеры буферов, проверяй границы.
- При выходе возвращай систему в исходное состояние: подсветка, вибро, LED, OTG,
  радио, GPIO-режимы.

## 8. Антипаттерны

| Плохо | Почему | Как лучше |
|---|---|---|
| `furi_delay_ms(500)` в draw/input | зависает весь GUI | таймер/событие/воркер |
| `malloc` в цикле отрисовки | фрагментация и просадки | кэш/переиспользование |
| `char buf[4096]` в callback | stack overflow | куча или статический буфер |
| `furi_record_open` без close | утечка/сбой других приложений | парность |
| `view_dispatcher_free` без remove_view | краш при выходе | remove перед free |
| Глобальные переменные состояния | мусор между запусками | поля `MyApp` |
| `printf` вместо `FURI_LOG_*` | нет тега/уровня, лишний код | `FURI_LOG_*` с `TAG` |
| Свой while-цикл вместо EventLoop | занятый поток, сложно остановить | `FuriEventLoop` |
| Игнорирование `FS_Error` | «пустые» файлы, непонятные баги | проверка + сообщение |
| Прямое использование внутренних функций | не экспортируется в API | только публичный API |
| Хранение `furi_string_get_cstr()` | указатель инвалидируется | копируй в буфер |

## 9. Стиль кода

- Язык — C11, стиль прошивки: `snake_case` функции/переменные, `PascalCase` типы,
  `UPPER_CASE` константы, префикс модуля (`my_app_...`).
- Заголовки: `#pragma once`, `extern "C"` для C++-совместимости.
- Приватные заголовки — `_i.h`.
- Комментарии — по делу, без пересказа кода; `/** ... */` для публичных функций.
- Форматирование — `ufbt format` (clang-format из репозитория).
- Не оставляй `TODO` без задачи; не коммить `printf`-отладку.
- Все пользовательские строки — короткие и понятные; для русского UI убедись, что
  шрифт содержит кириллицу.

## 10. Чек-лист ревью

- [ ] Нет блокирующих вызовов в GUI-callback-ах.
- [ ] Все ресурсы освобождаются на всех путях, включая ошибки и выход по Back.
- [ ] `stack_size` адекватен; большие буферы не на стеке.
- [ ] `view_dispatcher_remove_view` для каждого `add_view`.
- [ ] Обработаны ошибки storage/HAL, пользователю показано понятное сообщение.
- [ ] Нет обращения к внутренним символам прошивки.
- [ ] Логи с `TAG`, без секретов и мусора в горячем пути.
- [ ] UI корректен на 128×64, длинные строки не ломают вёрстку.
- [ ] После выхода устройство в исходном состоянии (свет, звук, радио, GPIO).
- [ ] Есть тесты для чистой логики; сборка `ufbt` без предупреждений.
