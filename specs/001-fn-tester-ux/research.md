## D1. Канонический байтовый слой и CRC (главная ловушка)

**Решение.** Ввести `lib/fn/core/fn_wire.{c,h}`:

```c
uint16_t fn_wire_u16le_get(const uint8_t* p);          // p[0] | p[1] << 8
void     fn_wire_u16le_put(uint8_t* p, uint16_t v);    // p[0] = v, p[1] = v >> 8
uint32_t fn_wire_u32le_get(const uint8_t* p);          // p[0] | p[1]<<8 | p[2]<<16 | p[3]<<24
void     fn_wire_u32le_put(uint8_t* p, uint32_t v);
uint16_t fn_wire_crc16_ccitt(const uint8_t* data, size_t len); // числовое значение
uint16_t fn_wire_crc16_read_le(const uint8_t* p);      // u16le в кадре
```

`calc_crc16()`, `check_crc()`, `two_uint8t_to_uint16t_LE/BE`,
`uint16t_LE/BE_to_uint8t_bytes`, `byte_array_to_uint32t_LE`,
`add_bytes_to_arr`, `prepend_data_to_array` удаляются **полностью** (без
алиасов-обёрток). Замена выполняется одним изменением (этап R1) вместе с
`core/fn_frame` и всеми вызовами.

Инварианты, закреплённые тестами:
- CRC считается по `LEN..DATA`, `MSG_START` не входит; init `0xFFFF`,
  полином `0x1021`, MSB-first; на проводе младший байт первым.
- `fn_wire_crc16_ccitt()` возвращает **число**, без перестановки байт.
  Перестановка существует только в `put/read_le`.
- API работает с `(data, len)`, а не `(start, end)`: исчезает «хотфикс»
  `end = end - 1`.
- Все функции проверяют `NULL` и нулевую длину (возврат 0 / no-op), а не
  падают; вызывающий код проверяет длину до чтения.

**Обоснование.** Сейчас имена противоположны смыслу: `two_uint8t_to_uint16t_LE`
читает big-endian, `..._BE` — little-endian; `uint16t_LE_to_uint8t_bytes`
пишет старший байт первым (big-endian на проводе). Внутри проекта всё
согласовано: `fn_trx()` собирает LEN через «`BE`», читает LEN и дни через
«`BE`», а CRC — через «`LE`» + `calc_crc16()`, который сам переставляет байты.
Поэтому «исправление по имени» без правки `calc_crc16`/`check_crc` ломает
парсинг. Канонический слой устраняет двусмысленность навсегда: имена
описывают провод, а не историческое недоразумение.

**Альтернативы.**
1. *Переименовать функции, оставив логику* — тогда `..._LE` начнёт врать в
   другую сторону; легко ошибиться в CRC. Отклонено.
2. *Оставить как есть и только задокументировать* — ловушка остаётся, новые
   команды будут добавляться с ошибками. Отклонено.
3. *Алиасы старого API для совместимости* — внешних потребителей нет,
   алиасы закрепляют путаницу. Отклонено.

**Проверка.** Golden-кадры из `.opencode/skills/fn-protocol/examples/frames.md`:
запросы `30h/31h/32h/33h/35h/3Ah/3Bh/3Dh/3Fh/60h` собираются
побайтово; ответы `30h` (обычный и с `0x80`), `32h`, `3Ah`, `3Bh`, `3Dh` (8 и 9
байт), ответ с ошибкой `03h` проходят `fn_frame_parse`. Дополнительно —
round-trip u16/u32 и тест «CRC не зависит от начального байта кадра».

## D2. Кодек кадра как чистый модуль

**Решение.** `lib/fn/core/fn_frame.{c,h}`:

```c
typedef struct {
    uint8_t cmd;         // команда или код ответа (сырой байт ANSWER)
    const uint8_t* data;
    size_t data_len;
    bool has_warning;    // (answer & 0x80) != 0
    uint8_t code;        // answer & 0x7F
} FnFrame;

typedef enum {
    FnFrameOk = 0,
    FnFrameNull, FnFrameTooShort, FnFrameTooLong,
    FnFrameWrongStart, FnFrameLengthMismatch, FnFrameWrongCrc,
} FnFrameStatus;

size_t fn_frame_build(uint8_t cmd, const uint8_t* data, size_t data_len,
                      uint8_t* out, size_t out_cap, FnFrameStatus* status);
FnFrameStatus fn_frame_parse(const uint8_t* buf, size_t len, FnFrame* out);
```

- Сборка — в буфер вызывающего; данных на стеке не больше 8 байт заголовка.
- `fn_frame_build` отказывается собирать кадр, если `data_len + 6 > out_cap` или
  `data_len > FN_FRAME_MAX_PAYLOAD` (256 − 6 = 250).
- `fn_frame_parse` не аллоцирует и не копирует: `out->data` указывает внутрь
  `buf`; время жизни — до конца обработки.
- Код ответа и предупреждение разделены: `frame.code`, `frame.has_warning`.

**Обоснование.** Сейчас сборка и разбор размазаны по `fn_trx()` внутри
`fn_tools.c`: ручные смещения (`tx[3]`, `rx_buff[4]`), `malloc` под TX и RX,
проверки длины и CRC вперемешку с бизнес-логикой, а ошибка длины делает
`fn_uart_stop_thread()` прямо из середины разбора. Вынесение в чистый модуль
делает кодек host-тестируемым и убирает дублирование смещений.

**Альтернативы.** Использовать `FlipperFormat`/`BitBuffer` — не подходит:
формат бинарный и простой, лишняя зависимость и код. Оставить `fn_trx` —
невозможно покрыть тестами на хосте и трудно поддерживать.

## D3. Парсеры с флагами достоверности

**Решение.** `proto/` содержит по функции на команду:

```c
bool fn_parse_status_30h(const uint8_t* d, size_t len, FnStatus* out);
bool fn_parse_session_10h(const uint8_t* d, size_t len, FnSession* out);
bool fn_parse_ffd_3ah(const uint8_t* d, size_t len, FnFfdInfo* out);
bool fn_parse_fw_33h(const uint8_t* d, size_t len, FnFwInfo* out);
bool fn_parse_end_date_32h(const uint8_t* d, size_t len, FnLifeDate* out);
bool fn_parse_end_days_3bh(const uint8_t* d, size_t len, FnLifeDays* out);
bool fn_parse_memory_3dh(const uint8_t* d, size_t len, FnMemory* out);
```

Структуры содержат `bool has_*` для необязательных/частичных полей. `len`
проверяется до каждого чтения. Функция возвращает `false` только если данных
недостаточно для обязательных полей; иначе `true` и заполненные `has_*`.

Исправляемые дефекты текущего разбора:
- `3Dh`: принимается 8 **или** 9 байт; процент маркировки — `data[8]` только
  при `len >= 9` и наличии флага `has_marking`; `data[data_len]` (выход за
  границу) удаляется.
- `3Dh`: `thirty_year_data_resource` → `thirty_day_data_resource` (КБ, 30 дней).
- `30h`: `serial_number[16]` больше не остаётся мусором — копируются 16 байт и
  ставится `'\0'` в `[16]` (буфер 17).
- `30h`: разбираются смещение 1 (текущий документ для ОФД) и 2 (признак
  «данные получены»), этап интерпретируется как маска (`1/3/7/15`).
- `30h`: дата/время проверяется на валидность (`month 1..12`, `day 1..31`,
  `hour < 24`, `minute < 60`); при невалидной дате `has_last_doc = false`.
- `32h`: поле `Date.mouth` → `month`.
- `3Bh`: дни читаются `u16le`; значение `0` трактуется как «нет данных» на
  уровне модели (`has_days_to_end = false`), а не как 0 дней.
- `10h`: новый парсер для номера смены и чека (этап 2).

**Обоснование.** Спецификация требует показывать «нет данных» вместо мусора и
сохранять остальные поля при отказе отдельной команды (FR-011, FR-027,
SC-012, SC-013). Модель «всё или ничего» этого не позволяет: сейчас любой сбой
`3Ah`/`33h` обнуляет уже полученные данные `30h`.

**Альтернативы.** Оставить структуры «плоскими» и передавать отдельные bool из
`fn_tools` — расползается по вызовам. Хранить длину и парсить лениво в UI —
нарушает принцип II (UI не должен знать протокол).

## D4. Модель времени: дедлайн операции и бюджет команды

**Решение.**

| Параметр | Значение | Смысл |
|---|---|---|
| `FN_CMD_TIMEOUT_MS` | 300 | ожидание ответа на одну служебную команду |
| `FN_OP_DEADLINE_READ_MS` | 10 000 | дедлайн операции чтения (FR-006) |
| `FN_OP_DEADLINE_FLASH_MS` | 30 000 | дедлайн очистки МГМ (FR-006, FR-023) |
| `FN_DETECT_ATTEMPTS` | 3 | попытки определения ФН в пределах дедлайна |
| `FN_RX_READY_WAIT_MS` | 100 | ожидание взвода DMA перед отправкой |

Операция чтения выполняется как последовательность команд, каждая с таймаутом
300 мс; при таймауте команда повторяется, пока не исчерпан общий дедлайн 10 с.
Таймаут операции — штатный исход `FnOpStatusNoResponse`, а не зависание.
Очистка МГМ — ровно одна отправка, без повторов, дедлайн 30 с.

**Обоснование.** Сейчас `fn_trx` ждёт `FuriWaitForever`, а 300 мс задаются
только таймером UART; при сбое UART-потока воркер зависает навсегда, и
`fn_worker_stop_thread()` не может завершиться (join). Дедлайн на уровне
операции делает поведение предсказуемым и соответствует SC-006.

**Альтернативы.** Один общий таймаут 10 с на команду — при 3 командах худший
случай 30 с, нарушает SC-006. Таймаут только на транспорте — не покрывает
случай «UART жив, ответа нет».

## D5. Воркер как одна типизированная операция

**Решение.**

```c
typedef enum {
    FnOpDetect, FnOpReadInfo, FnOpReadLife, FnOpFlashMgm
} FnOpKind;

typedef enum {
    FnOpStatusOk, FnOpStatusNoResponse, FnOpStatusFnRefused,
    FnOpStatusBadFrame, FnOpStatusCancelled, FnOpStatusBusy,
    FnOpStatusInternalError
} FnOpStatus;

typedef struct {
    uint32_t id;            // идентификатор запуска, защита от «поздних» событий
    FnOpKind kind;
    FnOpStatus status;
    FNError error;          // код ответа ФН (0 при отсутствии)
    bool has_warning;
} FnOpResult;

void fn_worker_start(FNWorker*, FnOpKind, FnTask* task, FnWorkerCallback, void* ctx);
void fn_worker_cancel(FNWorker*);
bool fn_worker_is_busy(const FNWorker*);
```

- `FnTask` — владелец выходных данных (`FnInfo`, `FnLifeInfo`), выделяется
  вызывающим; воркер только заполняет.
- Одна операция за раз: повторный старт возвращает `FnOpStatusBusy` через
  `furi_check` с `TAG` (нарушение контракта).
- Режимы `FNWorkerModeIdle/FNDetect/GetLifeInfo/FlashMGM` и поле
  `void* fn_answer_data` удаляются.
- `fn_worker_cancel()`: выставляет флаг остановки, прерывает ожидание
  (`furi_thread_flags_set`), вызывает `fn_uart_cancel()`, дожидается выхода
  операции и доставляет `FnOpStatusCancelled`. Для `FnOpFlashMgm` отмена
  игнорируется (возвращает `false`) — FR-015.
- Callback вызывается **из потока воркера** ровно один раз на операцию;
  UI-часть только отправляет custom event в dispatcher.

**Обоснование.** Сейчас `fn_worker_check_for_stop()` читает флаги текущего
потока и очищает их, `mode_index` меняется без синхронизации, а
`fn_worker_get_life_info_start()` копирует результат `memcpy` из временной
структуры. Типизированный результат и `op_id` убирают класс ошибок «сцена
показала результат предыдущей операции».

**Альтернативы.** Очередь запросов — избыточна: UI всегда ждёт одну операцию.
Промисы/корутины — нет в C без накладных расходов.

## D6. Транспорт: один буфер, one-shot таймер, отмена

**Решение.**
- Один `FuriStreamBuffer` ёмкостью `FN_FRAME_MAX_LEN` (256) в `UARTApp`;
  второй буфер в воркере удаляется — воркер читает кадр напрямую.
- `FuriTimer` — one-shot, взводится на первом байте приёма (RX-событие),
  останавливается на `Idle`; период не используется.
- Колбэк DMA не блокируется: `furi_stream_buffer_send(..., 0)`; при переполнении
  — флаг ошибки приёма, а не `FuriWaitForever`.
- Поток UART: `FuriThreadPriorityNormal` (вместо `FuriThreadPriorityIsr` —
  поток, который шлёт в stream buffer, не должен иметь ISR-приоритет).
- `fn_uart_alloc()` возвращает `NULL` при занятом порте (модуль expansion не
  отключился / порт занят), приложение показывает русское сообщение
  «Не удалось занять порт 13/14», а не падает по `furi_check`.
- `fn_uart_trx()`: без `furi_delay_ms`-цикла — ожидание `rx_ready` через
  флаги/событие с таймаутом 100 мс; состояние `busy` — `volatile bool`.
- `fn_uart_cancel()`: остановить таймер, очистить буфер, снять флаги, вернуть
  `Idle`; вызывается из `fn_worker_cancel()` и при выходе из приложения.
- `expansion_disable/enable` остаются парными, вызовы — в `alloc/free`.

**Обоснование.** Текущая схема «DMA → stream → колбэк → второй stream →
воркер» дважды копирует данные, а колбэк может блокироваться навсегда на
`FuriWaitForever` при полном буфере. Приоритет `Isr` у потока, делающего
`malloc`/stream-операции, — источник непредсказуемых задержек. Отмена
отсутствует вовсе.

**Альтернативы.** `FuriEventLoop` + `FuriEventLoopTimer` — современнее, но
добавляет зависимость и переписывание HAL-обвязки; для 115200 и кадров ≤256
байт достаточно stream buffer. Оставить два буфера — лишняя память и задержка.

## D7. UI: свои view, встроенный шрифт, сохранённая анимация

**Решение.**

| Экран | View | Модель |
|---|---|---|
| Главное меню | `FnMenuView` | 5 пунктов, выбранный индекс |
| Ожидание/определение | `FnWaitView` | режим (`Detect`, `Read`, `Flash`), строка статуса, флаг «можно прервать», анимация |
| Информация/результат/справка | `FnTextView` | массив секций `{title, lines[]}`, `scroll_y` |
| Подтверждение МГМ | `FnConfirmView` | текст, выбранная кнопка |

- Шрифт: собственный u8g2-массив с кириллицей (`ui/fn_font.c`), подключается
  `canvas_set_custom_u8g2_font`; два размера — основной (высота 8) и мелкий
  (высота 6). Генерация: BDF с нужными глифами → `bdfconv`/u8g2-конвертер →
  C-массив, результат коммитится, команда генерации описана в `docs/ui.md`.
- Анимация подключения: `A_FNLooking_64x64` остаётся; `icon_animation_start`
  в `enter`, `stop` в `exit`, `view_tie_icon_animation` — как сейчас. Анимация
  видна на всех экранах ожидания (detect и чтение данных), а не только на
  «Detecting».
- Логическая целостность блоков: информация строится как секции, заголовок
  секции никогда не отрывается от первой строки; прокрутка — по строкам, шаг
  равен высоте строки; длинные строки переносятся по ширине (не обрезаются).
- Прокрутка: `Up/Down` (и `Left/Right` как альтернатива), `elements_scrollbar`;
  `Back` — немедленный выход в меню независимо от позиции (FR-025).
- Строки — только из `ui/fn_strings.h` (русский). Латиница остаётся в SN, ФФД,
  версии ПО, URL.
- Стандартные модули (`submenu`, `widget`, `popup`, `dialog_ex`) в UI не
  используются и удаляются из `FNApp`; `dialogs` record не открывается.

**Обоснование.** Стандартные `submenu/widget` не дают кириллицу и не позволяют
управлять блоками/прокруткой; спецификация (Assumptions) прямо требует
собственной отрисовки и шрифта. Один `FnTextView` на все информационные экраны
убирает дублирование вёрстки `widget_add_text_*`, а один `FnWaitView` —
дублирование `detect`/`progress`.

**Альтернативы.** Транслит латиницей — нарушает FR-002 и SC-002. `TextBox` —
не поддерживает кириллицу без своего шрифта и не даёт секции/заголовки.
`widget` + `text_box_set_font` — нет управления блоками.

**Бюджет памяти.** Шрифт ≤6 КБ (два размера, subset ~200 глифов). Модели
экранов: меню ~64 Б, текст — статический пул строк (≤24 строки × 40 Б ≈ 1 КБ),
модель ожидания ~32 Б. Итого прирост ≤8 КБ; проверка `free` до/после.

## D8. Каталог кодов ответа с русскими текстами

**Решение.** `core/fn_error.{c,h}`: таблица «код → короткий русский заголовок →
подсказка» для всех кодов v1.2.05 (`00h`–`08h`, `09h`–`0Eh`, `10h`–`12h`,
`14h`, `16h`–`19h`, `20h`, `23h`, `24h`, `30h`, `32h`–`36h`, `3Ch`, `3Eh`).
API:

```c
const char* fn_error_title(FNError code);   // короткий текст для 128 px
const char* fn_error_hint(FNError code);    // рекомендация (может быть "")
bool        fn_error_is_known(FNError code);
```

Неизвестный код → «Неизвестный код ответа ФН: 0xNN» (форматируется в UI,
hex-строка, код ≥ `0x80` уже отмаскирован). Коды `02h`/`03h`/`04h` получают
подсказку «запросите 35h / перезапустите ФН», `12h`/`14h`/`16h` — «требуется
закрытие ФН/смены» (см. `response-codes.md`).

**Обоснование.** Сейчас `FNError` содержит 8 кодов, текстов нет вовсе
(`fn_errors.c` — пустая заготовка), UI показывает только «FN Error!». FR-029 и
SC-015 требуют русское описание для каждого кода протокола.

**Альтернативы.** Хранить текст прямо в `switch` UI — нарушает принцип II и
FR-029 (тексты должны быть в библиотеке). Генерировать строки из JSON —
лишняя инфраструктура для 40 констант.

## D9. Безопасность очистки МГМ

**Решение.**
1. Перед подтверждением выполняется `FnOpDetect` (30h + 33h). Если
   `fn_is_mgm()` ложно — показывается «Очистка недоступна: ФН не является МГМ»,
   команда не отправляется, Back возвращает в меню (FR-024, SC-009).
2. Для МГМ показывается `FnConfirmView` с предупреждением о необратимости;
   отказ — выход в меню без отправки (FR-012, FR-013, SC-004).
3. После подтверждения — `FnOpFlashMgm`, одна отправка, дедлайн 30 с,
   Back игнорируется до результата (FR-015, FR-023, SC-008).
4. Результат — `FnOpStatusOk` / `FnOpStatusFnRefused` + текст / `NoResponse`.
5. Повторная команда не отправляется ни по таймауту, ни по Back, ни по
   повторному входу в сцену.

**Обоснование.** `60h` не описана в Протоколе v1.2.05 и необратима; для
боевого ФН это недопустимая операция (принцип I конституции). Эвристика
`fw_mode == 0` — проектное знание, поэтому UI прямо называет признак
«МГМ (тестовый)», а не «тип ПО 0».

**Альтернативы.** Разрешать очистку всем — нарушает принцип I. Спрашивать
подтверждение после отправки — бессмысленно.

## D10. Стратегия тестирования

**Решение.**
1. `tests/host/` — `Makefile` + `cc`, компилирует `lib/fn/core/*.c` и
   `lib/fn/proto/*.c` (они не включают `furi.h`). Покрытие:
   - `fn_wire`: u16/u32 LE get/put, round-trip, границы;
   - `fn_frame`: сборка запросов из golden-набора, разбор всех эталонных
     ответов, усечённые/битые кадры, неверный CRC, неверный MSB-бит;
   - `proto/*`: каждый эталонный ответ, ответ с предупреждением, 8/9 байт
     `3Dh`, короткие ответы, невалидная дата, `08h`/`03h`;
   - `fn_error`: полнота таблицы (перебор кодов из заголовка), неизвестный код.
2. `unit_tests/` (устройство, `FN_TESTS=1`): те же модули (проверка, что код
   собирается под SDK) + транспорт (поток, отмена, таймаут) + воркер
   (детект/чтение/отмена/повтор после отмены) + реальный ФН с `[SKIP]`.
3. Приёмка UI — вручную по `quickstart.md` (US1–US5), при наличии —
   RPC-снимки экрана по скиллу `flipper-zero-app-dev`.
4. Регрессия памяти: `Leaked` до/после каждого прогона, `free` до запуска и
   после выхода, 10 циклов «операция → отмена» (SC-005).

**Обоснование.** Сейчас все тесты только на устройстве и требуют Flipper, а
`fn_helpers_test.c` закрепляет перепутанные имена как «правильные». Host-тесты
дают быстрый цикл и позволяют проверять границы буферов, что на устройстве
дорого. Устройство остаётся единственным источником истины для HAL и реального
ФН (принцип IV).

**Альтернативы.** Только устройство — медленно, нет покрытия границ.
Только хост — нарушает принцип IV и не проверяет HAL.

## D11. Память и ресурсы

**Решение.**
- `FN_FRAME_MAX_LEN 256`, `FN_FRAME_MAX_PAYLOAD (256 - 6)`, один RX-буфер,
  TX — в буфере вызывающего (максимум 11 байт для `3Bh`, 8 для `60h`).
- Никаких `malloc` по длине из ответа; парсеры работают по `(ptr, len)`.
- `FnInfo`/`FnLifeInfo` получают `fn_info_alloc/free`, `fn_life_info_alloc/free`
  с полной инициализацией (включая SN и флаги достоверности).
- Стек UART-потока пересматривается: 1024 → 1024 только если измерения `top`
  показывают запас; иначе 2048 с комментарием-обоснованием.
- Стек воркера 10240 остаётся (цепочка: операция → парсинг → логирование).
- `FNApp` освобождает все view/модели в обратном порядке, `fn_info` — через
  `fn_info_free`, worker — после остановки потока.
- Гейт этапа: `free` после выхода = baseline ±0, `top` без роста.

**Обоснование.** Принцип V и 256 КБ RAM: FAP целиком грузится в RAM, поэтому
и шрифт, и статические таблицы строк стоят RAM. Текущий код аллоцирует под
каждый ответ и держит два stream-буфера.

**Альтернативы.** Динамический `FuriString` для каждой строки экрана — фрагментация
и лишние alloc/free в GUI-потоке. Статические буферы больше нужного — прямой
расход RAM.

## D12. Структура, стиль и удаление мёртвого кода

**Решение.**
- Новые каталоги `lib/fn/{core,proto,transport}` и `ui/{views,scenes}`;
  имена файлов `fn_*`; идентификаторы английские, комментарии/строки русские.
- Удаляются: `scenes/fn_test_scene_test.c` (отладочный), `FNAppMode` с 7
  неиспользуемыми значениями, `dialog_ex`/`text_input`/`popup`/`submenu`/
  `widget`, `view_dispatcher_set_tick_event_callback` (никем не обрабатывается),
  `RECORD_DIALOGS`, `bool_to_hum()` (заменяется русскими «да/нет»),
  `prepend_data_to_array()` (не используется), `fn_test_app_i.h` — мёртвые
  `enum`/поля.
- Стиль: `TAG` + `FURI_LOG_*`, `furi_check/furi_assert` для контрактов,
  `snprintf`/`FuriString` для форматирования, `.clang-format` (`ufbt format`).
- Версия: `fap_version` (0, 6), запись в `.catalog/CHANGELOG.md`.

**Обоснование.** Полный рефакторинг запрошен явно; мёртвый код и
неиспользуемые зависимости мешают читать архитектуру и создают ложные связи.

**Альтернативы.** Косметические правки в существующих файлах — оставляют
ловушку в именах и дублирование экранов.

## D13. Документирование ловушки

**Решение.** `docs/byte-order.md` содержит:
- таблицу «старое имя → что делало → почему опасно»;
- правило: канонический слой `fn_wire`, имена описывают провод;
- перечень мест, где порядок байтов критичен (LEN, CRC, `3Bh`, `3Dh` u32,
  `30h` № ФД);
- инструкцию: при добавлении команды использовать только `fn_wire_*` и
  `fn_frame_*`, тест на golden-кадр обязателен;
- прямой запрет: «не «исправляйте» имя без правки CRC и всех вызовов».

Кроме того, предупреждение остаётся в `AGENTS.md` (раздел «Правила для агента»)
и в `docs/protocol.md`.

**Обоснование.** Ловушка уже стоила времени: она описана в скилле
`fn-protocol`, но не в репозитории; новый участник обязан узнать о ней из
кода/документа, а не из истории чата.

**Альтернативы.** Только комментарий в коде — теряется при рефакторинге.
