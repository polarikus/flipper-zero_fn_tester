# Контракт: события воркера, таймауты и отмена

**Слой**: `lib/fn/fn_worker.{c,h}`, `lib/fn/fn_ops.c`, `lib/fn/transport/*`
**Потребитель**: `ui/scenes/*`, `fn_test_app.c`.

## 1. События

```c
typedef enum {
    FNCustomEventWorkerResult = 0x100,  // единственное событие завершения операции
} FnCustomEvent;
```

- Значение `0x100` не пересекается с индексами меню (0–4) и кнопками.
- Событие отправляется ровно один раз на запущенную операцию — включая отмену.
- Полезная нагрузка в событие не помещается (uint32 недостаточно): callback
  воркера сначала записывает `FnOpResult` в `FNApp`, затем вызывает
  `view_dispatcher_send_custom_event()`.

### Порядок и потоки

```text
UI-поток (сцена)                Поток воркера                     Поток UART
     │ fn_worker_start()             │                                │
     ├──────────────────────────────>│ операция (команды, разбор)      │
     │                               ├──── fn_uart_trx() ────────────>│ DMA TX/RX
     │                               │<──── кадр / таймаут ───────────┤
     │                               │ FnOpResult → app->op_result     │
     │<── custom event (dispatcher) ─┤                                │
     │ читает app->op_result         │                                │
```

Гарантии:
1. Запись `app->op_result` происходит **до** `view_dispatcher_send_custom_event`;
   очередь dispatcher-а обеспечивает видимость данных в GUI-потоке.
2. Сцена проверяет `result.id == app->op_id`; событие с чужим `id`
   игнорируется с `FURI_LOG_W` (защита от «позднего» результата после отмены).
3. Callback не вызывает `scene_manager_*` напрямую и не блокируется.

## 2. Таймауты

| Константа | Значение | Область |
|---|---|---|
| `FN_CMD_TIMEOUT_MS` | 300 | ожидание ответа на одну команду |
| `FN_OP_DEADLINE_READ_MS` | 10 000 | дедлайн операций `Detect`, `ReadInfo`, `ReadLife` |
| `FN_OP_DEADLINE_FLASH_MS` | 30 000 | дедлайн `FlashMgm` |
| `FN_RX_READY_WAIT_MS` | 100 | ожидание взвода RX DMA перед отправкой |

Правила:
- Дедлайн считается от `furi_get_tick()` в момент `fn_worker_start`.
- Перед каждой командой проверяется остаток дедлайна: если он меньше
  `FN_CMD_TIMEOUT_MS`, команда не отправляется, операция завершается
  `NoResponse`.
- Повтор команды разрешён только для чтения и только в пределах дедлайна.
  `FlashMgm` — одна отправка, повторов нет (принцип I).
- По истечении дедлайна транспорт обязательно приводится в `Idle`
  (`fn_uart_cancel`), флаги и буферы сбрасываются.

## 3. Отмена

```c
void fn_worker_cancel(FNWorker* worker);   // не блокирует
bool fn_worker_is_busy(const FNWorker* worker);
```

| Операция | Отменяема | Поведение Back в UI |
|---|---|---|
| `FnOpDetect` | да | отмена + немедленный переход в меню |
| `FnOpReadInfo` | да | отмена + немедленный переход в меню |
| `FnOpReadLife` | да | отмена + немедленный переход в меню |
| `FnOpFlashMgm` | **нет** | Back игнорируется, ждём результат/30 с |

Механика отмены:
1. `fn_worker_cancel` выставляет флаг `cancel_requested` и будит поток воркера
   (`furi_thread_flags_set`).
2. Воркер прерывает текущее ожидание, вызывает `fn_uart_cancel()`.
3. Незавершённая команда не повторяется; результат — `FnOpStatusCancelled`,
   `error = FNOk`.
4. Callback вызывается один раз; сцена уже в меню, поэтому событие
   отбрасывается по `id`.
5. Время от вызова до `Idle` — не более 1 с (SC-003).

Запрещено:
- отменять `FlashMgm` (в том числе «на всякий случай» при выходе);
- отправлять повторную команду после отмены без нового подтверждения;
- уходить из приложения при активной операции: `fn_worker_free` проверяет
  `!busy`.

## 4. Матрица исходов

| Что произошло | `FnOpStatus` | `error` | `has_warning` | Что видит пользователь |
|---|---|---|---|---|
| Все команды вернули `00h` | `Ok` | `FNOk` | по ответу | данные / «Успешно» |
| Ответ с битом `0x80` | `Ok` | `FNOk` | `true` | данные + блок предупреждений |
| Код `03h`/`04h`/`12h`… | `FnRefused` | код | — | русский текст + подсказка |
| Нет байт до дедлайна | `NoResponse` | `FNOk` | `false` | «ФН не отвечает» |
| CRC/`LEN`/`START` неверны | `BadFrame` | `FNOk` | `false` | «Повреждённый ответ ФН» |
| Отмена пользователем | `Cancelled` | `FNOk` | `false` | ничего (уже в меню) |
| Воркер занят | `Busy` (без callback) | — | — | «Подождите, идёт операция» |
| Сбой инициализации порта | `InternalError` | `FNOk` | `false` | «Не удалось занять порт 13/14» |
| Необязательная команда отказала (`10h`, `3Bh`, `3Dh`) | `Ok` | `FNOk` | — | остальные блоки + «нет данных» |

Уточнение: отказ необязательной команды **не** делает операцию `FnRefused`,
если основные данные получены (FR-011, FR-027); код отказа сохраняется для
диагностики в `FURI_LOG_W`.

## 5. Инварианты воркера

1. В любой момент времени активна не более одной операции.
2. Операция всегда завершается одним из статусов, перечисленных в §4; «вечного
   ожидания» нет.
3. После завершения операции: транспорт `Idle`, буферы пусты, флаги сброшены,
   `worker->busy == false`.
4. `fn_worker_free` вызывается только при `!busy`; поток останавливается
   (`fn_worker_stop_thread`) до освобождения UART.
5. Ошибки контракта (повторный `start` без ожидания, `NULL` task) —
   `furi_check` с `TAG`.
6. Логи: старт операции (`info`), каждая команда (`debug`), завершение со
   статусом (`info`), отмена и поздние события (`warn`).

## 6. Тестовые сценарии (обязательные)

| Сценарий | Ожидание |
|---|---|
| `Detect` с реальным ФН | `Ok`, поля заполнены, `id` совпадает |
| `Detect` без ФН | `NoResponse` ≤ 10 с |
| `ReadInfo` дважды подряд | оба `Ok`, `id` растёт, данные не «залипают» |
| `ReadInfo` → `cancel` через 100 мс | `Cancelled` ≤ 1 с, следующая операция `Ok` |
| 10 циклов «операция → отмена» | 11-я операция `Ok`, утечек нет (SC-005) |
| `FlashMgm` на боевом ФН | команда не отправлена (проверка на уровне сцены + лог) |
| `FlashMgm` с `cancel` во время ожидания | отмена игнорируется, результат по факту/30 с |
| Битый CRC в ответе | `BadFrame`, транспорт `Idle`, следующая операция `Ok` |
| Ответ с `0x80` | `Ok` + `has_warning`, флаги в UI |
| Занятый USART (модуль expansion) | `InternalError`, приложение не падает |
